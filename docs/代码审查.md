### 问题清单

#### 🔴 严重问题

**问题1：启动加载与用户命令并发，可能覆盖用户刚创建的数据**
- 位置：`ViewModels/MainWindowViewModel.cs:91-92`、`94-110`
- 问题：构造函数以 fire-and-forget 方式启动 `LoadTasksFromStorageAsync()`，主窗口立即可操作；加载完成后会执行 `_allTasks.Clear()` 并用磁盘数据重建列表。
- 风险：应用启动后用户快速添加/删除任务时，异步加载可能随后清空这些修改；未保存的数据会直接消失。
- 建议：增加显式初始化流程（例如 `InitializeAsync`/启动状态门禁），初始化完成前禁用编辑命令；或在应用生命周期中先完成加载再显示主窗口。不要在构造函数中启动未被持有的任务。

**问题2：自动保存使用 `async void`，多次保存可并发写文件且无法保证最后一次状态落盘**
- 位置：`ViewModels/MainWindowViewModel.cs:118-130`、`204-216`
- 问题：每次新增、删除、勾选都会调用 `TriggerAutoSave()`；方法为 `async void`，没有串行化、取消旧保存或等待退出前保存的机制。
- 风险：快速连续操作时会有多个 `File.WriteAllTextAsync` 同时写同一个文件，后完成的旧快照可能覆盖新快照；关闭应用时也可能仍有后台写入，造成数据丢失或 JSON 截断。
- 建议：引入单一写入队列/`SemaphoreSlim`，采用 debounce 或版本号丢弃旧快照；保存返回 `Task` 并由应用关闭流程等待；存储服务实现 `IAsyncDisposable`/显式 Flush。

**问题3：持久化失败被吞掉，UI 会错误显示“已自动保存”**
- 位置：`Services/JsonTodoStorageService.cs:69-81`、`ViewModels/MainWindowViewModel.cs:122-129`
- 问题：`SaveAsync` 捕获所有异常后只写日志并正常返回，调用方无法区分成功与失败，随后无条件设置 `StorageStatus = "数据已自动保存"`。
- 风险：磁盘满、权限不足、文件被占用等生产故障对用户不可见，用户以为数据已保存，重启后才发现丢失。
- 建议：让存储层返回明确结果或重新抛出领域异常；ViewModel 根据结果显示失败状态并提供重试/打开数据目录入口。错误消息不要直接暴露原始异常文本，可记录详细日志、对用户显示可操作的摘要。

**问题4：更新服务是固定延迟和硬编码版本，且版本比较使用字符串比较**
- 位置：`Services/UpdateService.cs:22-45`
- 问题：没有网络请求、超时、取消、签名/哈希校验；最新版本固定为 `1.1.0`，下载地址固定为 Avalonia 官方仓库。`string.Compare` 不能正确比较 `1.10.0` 与 `1.9.0` 等语义版本。
- 风险：用户会被引导到错误下载地址；版本提示不反映真实发布状态，正式环境可能误升级、漏升级或无法验证下载包完整性。
- 建议：使用可注入的 `HttpClient` 和明确的更新源 DTO；用 `NuGet.Versioning` 或等价 SemVer 实现比较；增加超时、取消、网络错误分类、HTTPS/允许域校验、包哈希或签名校验，并将当前版本从统一构建元数据读取。

#### 🟡 建议修改

**问题5：应用生命周期与 DI 容器职责混杂，服务提供器未释放**
- 位置：`App.axaml.cs:15`、`23-29`、`47-56`
- 问题：`App` 持有静态 `IServiceProvider`，同时作为 Service Locator 被 View 层直接调用；`BuildServiceProvider()` 创建的容器没有在应用退出时释放。
- 建议：把 DI 组合根集中到 `Program`/Host，窗口通过构造函数注入；在 `Shutdown` 中释放 `IHost`/`ServiceProvider`。当前规模不必引入复杂框架，但应至少移除业务代码对 `App.Services` 的直接依赖。

**问题6：默认构造函数直接 `new` 基础设施，绕过 DI 并降低可测试性**
- 位置：`ViewModels/MainWindowViewModel.cs:82-84`
- 问题：生产类保留无参构造并直接创建 `JsonTodoStorageService`、`UpdateService`，导致依赖配置出现两套来源。
- 建议：删除无参构造，只保留构造函数注入；如果设计工具需要无参实例，使用专用设计时 DataContext，而不是在生产 ViewModel 中保留后门。

**问题7：窗口关闭行为与注释不一致，实际是隐藏而不是最小化**
- 位置：`Views/MainWindow.axaml.cs:17-24`
- 问题：注释和界面文案描述“最小化到托盘”，实现只调用 `Hide()`，没有设置 `WindowState = Minimized`；不同平台的关闭/退出语义也没有统一的生命周期服务。
- 建议：明确产品语义（隐藏或最小化），按平台验证托盘行为；把关闭策略放入生命周期/窗口协调服务，并在退出前等待保存完成。

**问题8：更新按钮文本绑定逻辑不正确**
- 位置：`Views/AboutUpdateWindow.axaml:106-117`
- 问题：`Text="{Binding IsChecking, Converter={x:Null}, FallbackValue='检查更新'}"` 会把布尔值直接显示为 `True/False`；`FallbackValue` 只在绑定未解析时生效，不会根据状态显示中文文案。
- 建议：增加 `CheckUpdateButtonText` 计算属性，或使用明确的 Boolean-to-string Converter，并补充加载中、成功、失败三种状态的 UI 测试/验收。

**问题9：日志基础设施与用户可见错误处理不统一**
- 位置：`Program.cs:15-19`、`Services/LogHelper.cs:20-27`、`AboutUpdateViewModel.cs:114-116`
- 问题：日志目录创建发生在静态初始化阶段，失败可能早于全局异常兜底；打开下载地址失败使用 `Debug.WriteLine`，不会进入正式日志。全局异常处理只记录异常，不提供用户提示或崩溃报告导出。
- 建议：日志初始化应可失败降级（stderr/临时目录），所有服务统一使用 `ILogger`/Serilog；增加崩溃上下文、版本、操作系统、最近操作等诊断信息，并注意脱敏。

**问题10：时间模型使用本地时间，跨时区和文化环境下不可稳定复现**
- 位置：`Models/TodoItem.cs:13`、`ViewModels/TodoItemViewModel.cs:23`、`Services/UpdateService.cs:43`
- 问题：实体保存 `DateTime.Now`，显示格式也未指定 Culture；数据迁移、排序和跨时区同步时语义不明确。
- 建议：持久化使用 UTC（`DateTimeOffset` 优先），展示层按当前区域格式化；定义统一的时钟抽象，便于测试。

**问题11：JSON 文件没有版本、原子替换和损坏恢复策略**
- 位置：`Services/JsonTodoStorageService.cs:31`、`54-75`
- 问题：直接覆盖目标文件；反序列化失败时返回空列表但不备份损坏文件，也没有 schema/version 字段和迁移机制。
- 建议：采用 `{ schemaVersion, items }` 包装结构；写入临时文件后 flush，再使用原子替换；读取失败时保留 `.corrupt.<timestamp>` 备份并向 UI 报告恢复状态。数据量增长后再评估 SQLite，当前无需立即引入数据库。
